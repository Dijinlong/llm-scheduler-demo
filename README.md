# llm-scheduler-demo

多货源派单的最小实现：**滑动窗口健康分 + 熔断 + 带探索的加权选择**。

一个反直觉的结论：同样的货源池，轮询派单的 429 率可能是分数派单的 6 倍——因为你把「便宜但脆弱」的货源平等地放进了主路径。

```
轮询派单    429 占比 15.98%
健康分派单  429 占比 2.74%
降幅        82.9%
```

（模拟结果：3 个货源，真实 429 概率分别为 2% / 10% / 35%，2 万次请求。）

---

## 跑起来

```bash
go run scheduler_demo.go
```

只用标准库，无依赖。改 `main()` 里的三个参数（价格系数、失败率），能看到不同参差程度下的差距。

## 三个核心机制

### 1. 60 秒滑动窗口健康分

```go
if sm.tooMany {
    bad += 2          // 429 双倍扣分
} else if !sm.ok {
    bad++
}
h := 1 - bad/total
```

- 窗口 60 秒：足够反映「现在行不行」，又不会被一次抖动影响太久
- 样本 < 5 条时给 0.8 起步分：否则新货源永远拿不到流量，也就永远没有数据

### 2. 分数 = 健康分² ÷ 价格系数

```go
score := (h * h) / s.PriceRatio
```

- 除以价格系数：便宜的占优，这是商业目标
- 平方：健康度 0.9 → 0.6，分数不是掉 1/3，而是掉一半多
- 前 3 名加权抽签：避免流量 100% 压在第一名，把它变成下一个被打爆的

### 3. 熔断 + 半开 + 指数退避

连续 3 次 429 熔断，冷却 20s 起翻倍、封顶 5 分钟；冷却结束进入半开，**只放一个探针**，成功才恢复。

---

## 两个容易被忽略的保护

**5% 探索流量**：纯按分数派单，掉分的货源永远无法证明自己恢复了。留 5% 随机投放。

**最小可用集**：健康货源 < 2 个时忽略熔断，选当前最好的那个。可用集越小，剩下的人死得越快——宁可慢，不能全断。

---

## 上线前想清楚的四件事

1. **重试要换货源，不要原地重试**——同一货源重试等于加倍压力
2. **区分模型级 429 和账号级 429**——后者换货源没用，背后是同一个账号池
3. **有 `Retry-After` 就照做**，没带的退避要加抖动，否则重试会在同一毫秒同步
4. **分母是总请求**，不是错误数——否则数字永远好看

---

## 什么时候不该用

- 货源少于 3 个：没得选
- 所有货源同一个上游：429 是同步的，换谁都一样
- 流量低于 100 QPS：先修超时和重试次数，收益更大
- 没有按账号/模型维度记录 429：先补日志
